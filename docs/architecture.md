# Архитектура MyOS 0.5.0-dev

## Назначение

MyOS — учебно-практическое ядро собственной разработки для **x86_64**. Один гибридный ISO-образ запускается через BIOS или UEFI в QEMU и предназначен для последующего теста с выделенного USB-носителя на физическом ПК. Развитие идёт от наблюдаемого консольного ядра к изолированным процессам, файловой системе и графической среде.

> Limine подготавливает среду запуска и передаёт управление `kmain`, но не входит в ядро. Слои памяти, прерываний, драйверов, консоли, процессов и будущего GUI принадлежат MyOS. [1]

## Слои системы

| Слой | Каталог | Ответственность в 0.5.0-dev | Следующая граница |
|---|---|---|---|
| Загрузка | `boot/` | Higher-half ELF layout, заявки Limine, BIOS/UEFI меню. | Сформировать единый `boot_info` и явно зарезервировать bootstrap-ресурсы. |
| Архитектура | `kernel/arch/x86_64/` | GDT, IDT, exception/IRQ stub, портовый I/O, Local APIC virtual-wire. | Page-fault policy, APIC timer, IOAPIC, SMP. |
| IRQ и драйверы | `kernel/irq/`, `kernel/drivers/` | PIC 8259A, PIT 100 Гц, PS/2 Set 1 и кольцевой буфер клавиатуры. | USB HID, расширенные клавиши, очереди устройств. |
| Память | `kernel/mm/` | Bitmap PMM, собственный PML4, 4 KiB mapper, Local APIC MMIO и monotonic heap. | `kfree`, page ownership, unmap и user mappings. |
| Консоль | `kernel/console/` | Shell через COM1 и PS/2, ожидание `hlt`, команды диагностики памяти. | Шрифт и text console поверх framebuffer. |
| Ядро | `kernel/main.c` | Последовательность bootstrap, переход на собственный CR3, включение IRQ. | Декомпозиция на `boot_info`, init stages и panic framework. |
| Пользовательская среда | `user/` | Пока отсутствует. | Ring 3, syscalls, ELF и initramfs. |

## Порядок запуска

Limine запускает `kmain` в long mode и публикует ответы на статические заявки. MyOS создаёт serial log, GDT и IDT, затем строит bitmap PMM по карте физической памяти. Следом `paging_take_control()` выделяет новую PML4, копирует текущие рабочие PML4 entries и загружает новый CR3. Это сохраняет kernel mapping и HHDM, предоставленные загрузчиком, но делает новые page table mutations собственностью MyOS.

После перехода mapper создаёт 4 KiB PML4/PDPT/PD/PT цепочки по требованию. Local APIC получает отдельную некэшируемую MMIO-страницу. Затем стартуют PIC, PIT и PS/2, разрешаются IRQ0 и IRQ1, включается IF. Каждое новое отображение проходит проверку выравнивания и каноничности, а после изменения доступной страницы TLB инвалидируется через `invlpg`. Многоуровневые таблицы уменьшают расход памяти для разреженных виртуальных диапазонов и образуют аппаратный путь от виртуального адреса к физической странице. [2] [3]

## Адресное пространство

| Диапазон | Назначение | Политика 0.5.0-dev |
|---|---|---|
| Higher-half kernel | ELF-код, данные и стек, созданные загрузчиком. | Bootstrap mapping копируется при создании нового PML4. |
| HHDM | Доступ к физической памяти и page-table кадрам. | Используется PMM и mapper до самостоятельного управления всей картой. |
| `0xFFFFFFFFC0000000` | Local APIC. | 4 KiB, supervisor RW, PWT+PCD. |
| `0xFFFF900000000000` | Kernel heap, максимум 1 GiB. | 16-byte allocation alignment, новые 4 KiB страницы выделяются лениво. |
| Низкая половина | Резерв будущего user space. | Новые user mappings пока не создаются. |

## Heap и диагностика

Kernel heap — намеренно компактный bump allocator. `kmalloc()` округляет запрос до 16 байт, при пересечении следующей 4 KiB границы запрашивает кадр у PMM и создаёт supervisor-only mapping. Память обнуляется до возврата вызывающему коду. Пока `kfree()` отсутствует, поэтому heap подходит для ранних долгоживущих объектов, а не для неограниченных временных аллокаций.

| Команда shell | Назначение |
|---|---|
| `paging` | Показывает active PML4, число новых MyOS mappings и физический адрес Local APIC. |
| `heap` | Показывает used/capacity, число отображённых страниц и выделений. |
| `heaptest` | Выделяет 64 байта и блок размером `4096 + 64`, записывает и читает маркеры через границу страницы. |
| `ticks`, `irqs`, `keyboard` | Подтверждают, что PIT, Local APIC и PS/2 продолжают работу после CR3 switch. |

## Неподдерживаемое пока

Отсутствуют освобождение heap, обработка page fault как политика восстановления, защита write/execute по секциям, пользовательские U/S mappings, COW, swap, IOAPIC и графическая текстовая консоль. Эти ограничения известны и являются границами текущего контрольного результата, а не скрытыми обещаниями совместимости.

## Следующая техническая итерация

Следующая версия должна укрепить ownership памяти: зарезервировать страницы ядра и модулей, добавить page-fault decoding, guard pages и free list для heap. После этого MyOS сможет начать framebuffer-терминал, который заменит текущую зависимость от COM1 для обычного интерактивного запуска.
